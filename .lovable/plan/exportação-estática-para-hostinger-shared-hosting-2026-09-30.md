# Exportação estática para Hostinger Shared Hosting

## Conclusão
É possível publicar o visual, as cinco páginas, a navegação, as animações, os filtros e o formulário sem Node.js no computador nem no servidor, desde que o pacote seja gerado **antes** em um ambiente de build remoto (por exemplo, CI). Há uma exceção funcional: a Central de Atualizações usa hoje uma função no servidor para consultar os feeds oficiais; ela precisa passar a receber dados estáticos gerados no build. Assim, as notícias não se renovariam sozinhas apenas porque o site está na Hostinger. Para atualização automática, seria necessário agendar novas gerações e envios do pacote fora da hospedagem compartilhada. Nenhuma alteração ou publicação será feita nesta etapa.

## Alterações propostas
1. Configurar uma exportação separada para hospedagem estática, preservando a configuração atual do projeto no Lovable. Pré-gerar HTML para `/`, `/quem-somos`, `/servicos`, `/blog` e `/contato`, com os respectivos metadados. Confirmar que abrir ou atualizar cada URL diretamente funciona na Hostinger; adicionar regras Apache pontuais apenas se necessárias, sem substituir páginas reais por uma página única.
2. Trocar a leitura em tempo real dos feeds da Central de Atualizações por um arquivo de notícias produzido por um script de build remoto a partir das mesmas fontes oficiais. Reaproveitar normalização, filtros, ordenação e deduplicação; manter os conteúdos anteriores e os links originais. Se algum feed falhar, usar a última versão válida disponível, sem inventar notícias. Explicitar a data da última atualização se o conteúdo ficar estático. Para atualizar as notícias automaticamente, agendar o build e a publicação do pacote por CI; se isso não for configurado, atualizar manualmente via novo build.
3. Substituir as referências às nove imagens usadas via caminhos exclusivos da infraestrutura Lovable (`/__l5e/assets-v1/...`) por arquivos locais incluídos no pacote estático, mantendo exatamente as imagens e suas proporções. Incluir também imagens já locais, CSS, fontes de terceiros já referenciadas e favicon; verificar se nenhum recurso essencial busca um caminho exclusivo do Lovable.
4. Manter o formulário atual enviando diretamente, via POST no navegador, para `https://formspree.io/f/xqpajyza`, com campos, validações e mensagens de sucesso/erro. Testar o envio e a política de acesso do Formspree a partir do domínio final antes de considerar a migração concluída. O mapa do Google e links externos continuam dependentes desses serviços, não de Node na Hostinger.
5. Validar o pacote em um servidor de arquivos estáticos, inclusive carregamento direto e atualização das cinco URLs, filtros da Central, imagens, layout desktop/mobile e formulário; inspecionar o pacote para garantir que nenhuma rota ou requisição precise de função de servidor em produção.

## Detalhes técnicos e pasta de saída
- O projeto usa TanStack Start, e o build atual inclui um servidor; copiar o resultado atual inteiro para `public_html` **não** basta. Em um build externo ao ambiente Lovable, a configuração estática proposta usa o preset `nitro: { preset: "static" }` e pré-renderização de todas as cinco rotas, após remover a dependência de `createServerFn` da Central. O preset instalado define a pasta pública como **`.output/public/`**: somente **o conteúdo dessa pasta**, após validação do build real, iria para `public_html/`. A pasta exata e os arquivos gerados devem ser confirmados em um build de prova; ainda não foi executado nenhum build estático.
- O build hospedado do Lovable fixa outro formato de saída e não aceita esse preset estático; portanto, seria necessário executar o build em CI externo, não no PC e não na Hostinger. Node.js seria usado **somente durante o build remoto**, não para servir o site.
- URLs limpas como `/blog` devem apontar para HTML pré-gerado (`blog/index.html`). Um fallback Apache pode cobrir casos não existentes, mas não deve eliminar o HTML e SEO individuais de cada página. Parâmetros como `?categoria=Importação` continuam controlados no navegador.
- Esta proposta não inclui mudança de domínio, DNS, hospedagem nem publicação. A atualização automática dos feeds dependerá da configuração futura de CI agendado e das credenciais de envio da Hostinger, nunca embutidas no código.
